Security Threat Checklist

A living checklist for the BeyondTheMatrix.video / R2 media infrastructure project

This page is intentionally a checklist, not a claim that every item is already solved. The purpose is to make sure every important threat has an owner: Cloudflare, Render, our application, or some combination of the three.

Rule: "Behind Cloudflare" does not mean "secure." Cloudflare and Render can remove enormous classes of network attacks before they reach us, but requests that look like legitimate application traffic still require correct application design.

Status Key

  • Platform covered - the platform provides the primary control; we still verify configuration and behavior.
  • Design / implement - primarily our responsibility and must be addressed in the application or Worker.
  • Ongoing - cannot be considered permanently "done"; requires monitoring, patching, rotation, or review.
  • Future - relevant to later live-streaming, multi-tenant, or production ingest phases.
Threat Cloudflare Render Our Responsibility Status Test / Verification
L3/L4 DDoS
SYN floods, UDP reflection, volumetric attacks		 Primary edge mitigation. All inbound Render web-service traffic passes through Cloudflare; Render says L3/L4 floods are fully mitigated before the app. Keep architecture behind protected entry points; monitor unexpected behavior. Platform covered Document current topology and confirm no unintended public origin path.
Layer-7 DDoS / resource exhaustion
HTTP floods, expensive endpoints		 WAF, DDoS heuristics, custom rules and rate limiting can help. Large obvious floods receive edge filtering; targeted abuse may still reach the application. Protect expensive endpoints; adaptive limits; graceful degradation; application-aware monitoring. Design / implement Load-test login, search, API and expensive database paths.
Origin bypass / alternate hostname Can protect custom domains and Workers. Every web service also has an onrender.com hostname. Do not assume all traffic passed through rules attached only to our custom Cloudflare zone. Decide whether alternate-host access should be restricted. Review Request the service through every known hostname and compare protections.
Credential stuffing / account takeover Rate limiting, WAF and bot controls can assist. Render explicitly identifies targeted credential stuffing as an application responsibility. Strong authentication, login throttling, MFA/passkeys where appropriate, session alerts, password reset protection. Design / implement Simulate repeated distributed login failures and account recovery abuse.
Automated scraping / bot abuse Bot controls, challenges and rate limits can reduce automated abuse. No application-specific protection promised. Decide what may be public, authenticated, indexed, downloaded or bulk-accessed. Apply quotas and authorization accordingly. Design / implement Test slow distributed scraping as well as obvious high-rate scraping.
API authorization failures / BOLA
User A requests User B's object		 Cannot determine business ownership of an object for us. Cannot determine application authorization for us. Entirely ours: authorize every object/action server-side. Never trust object IDs, tenant IDs or UI visibility. Critical - design Automated cross-user and cross-tenant access tests on every object API.
Tenant isolation failure Workers can enforce tenant routing, but only if we write the rules correctly. Hosting isolation does not understand our tenant model. Entirely ours: tenant identity must be validated at every storage, metadata, cache and authorization boundary. Critical - design Create deliberate cross-tenant attempts for reads, writes, listings, cache keys and signed playback.
Session hijacking / token theft / replay Edge enforcement can validate signed or session-based access. Provides hosting/TLS, not our session policy. Secure cookies, short lifetimes, absolute expiry, rotation, revocation strategy and anomaly detection. Design / implement Copy tokens between browsers/devices and confirm intended expiry/replay behavior.
Hotlinking / unauthorized media playback Worker/WAF rules can enforce playback policy. Not a media authorization layer. Playback authorization, tenant policy, token/session validation and cache-key correctness. Design / implement Embed protected media from an unauthorized site and attempt direct segment/object access.
SSRF
Server is tricked into fetching internal or dangerous URLs		 May block some malicious requests at the edge but cannot safely validate our outbound-fetch logic. Platform isolation helps limit blast radius but does not fix unsafe fetch behavior. Strict URL validation, block loopback/private/link-local destinations, redirect controls, outbound policy and isolated processing. Design / implement Attempt localhost, RFC1918, link-local, IPv6-local and redirect-chain targets.
XSS / client-side injection WAF can catch some exploit patterns; CSP-related products can assist. Can set response headers, but application output remains ours. Output encoding, input handling, CSP, secure templates, avoid unsafe DOM injection. Design / implement Automated and manual tests against every user-controlled field rendered in HTML/JS.
Third-party JavaScript / supply-chain compromise Can assist with client-side visibility/security products. Does not validate third-party browser code. Minimize dependencies, use CSP/SRI where appropriate, pin versions, review what executes in the browser. Ongoing Inventory all third-party scripts and browser-accessible data.
Dependency / package compromise May shield exploitation attempts but does not make vulnerable code safe. Maintains platform infrastructure; our packages remain ours. Pin dependencies, vulnerability scanning, controlled upgrades, reproducible builds where practical. Ongoing Routine dependency audit and patch process.
Secret / API-key leakage Protect account/API tokens with least privilege and rotation. Environment/secret facilities help keep secrets outside source code. Never ship secrets to browsers or repositories. Least privilege, separation by environment, rotation and emergency revocation. Critical - ongoing Secret scan repository/build artifacts; document revocation procedure.
Unauthorized or malicious uploads Can enforce request size/rate/policy at the edge. Provides compute isolation, not semantic validation of our media. Authenticate uploaders; validate type/size; never trust filename or MIME alone; isolate processing; enforce storage quotas. Design / implement Upload malformed, oversized, misleading and unexpected file types.
Media parser / transcoder exploits Not the primary defense. Hosting isolation can reduce blast radius. Keep ffmpeg/media libraries patched; run untrusted processing with minimal privileges and isolation. Future / ongoing Fuzz/malformed-media testing and processor isolation review.
Stream-key / ingest credential theft Can provide protected ingest front doors depending on architecture. Not application-specific. Short-lived or rotatable ingest credentials, scoped permissions, secure producer onboarding. Future Revoke/rotate a compromised key without disrupting unrelated streams.
Cache poisoning / cache-key mistakes Cloudflare executes the cache policy we configure. Not responsible for our Cloudflare cache semantics. Never allow authentication/tenant state to collide in cache keys. Normalize carefully and test authenticated/anonymous variants. Critical - design Cross-user and cross-tenant cache tests before production.
DNS / domain / control-plane account takeover Account security, scoped API tokens and MFA/passkeys are essential. Render account security is equally important. Protect registrar, Cloudflare, Render and source-control accounts; hardware/passkey MFA where practical; emergency recovery documented. Critical - ongoing Review admins, recovery methods, tokens and unused access quarterly.
Bad deployment / configuration error Cannot protect us from incorrect Worker/WAF/cache logic. Health checks, zero-downtime deploys and rollback features can reduce impact. Staging, health checks, configuration review, fast rollback and change logging. Ongoing Practice rollback and verify health checks detect a deliberately bad build.
Data loss / accidental deletion / destructive account compromise R2 durability is infrastructure protection, not a substitute for our recovery plan. Application hosting does not replace media backup/recovery. Versioning/backup/archive strategy, immutable source masters where appropriate, inventory and restore testing. Design / implement Perform a real restore from backup/versioned storage.
Logging blind spots / slow attack detection Security events and request identifiers provide edge visibility. Render forwards CF-Ray and recommends logging it. Adaptive Traffic Monitoring, structured logs, alert thresholds and enough retention to investigate incidents. Design underway Generate a known anomaly and verify detection, logs and operator visibility.
Adaptive / low-and-slow abuse Rate limiting and bot/WAF signals can assist. Render explicitly notes slow and targeted requests may reach the app. Our Adaptive Traffic Monitoring layer watches changes in request velocity, distribution, cost and behavior rather than only raw volume. Design underway Simulate distributed traffic below simple per-IP thresholds.

Operational Rule

Every new feature should get a quick pass through this checklist before it is considered production-ready. If a new threat appears during research or testing, add a row rather than relying on memory.

Useful Platform Boundaries

  • Cloudflare: strongest at edge/network filtering, WAF, rate controls, bot signals, request enforcement and protected media delivery.
  • Render: protected application hosting, Cloudflare-backed inbound DDoS protection, load balancing, health checks and deployment/runtime controls.
  • Us: authentication, authorization, tenant isolation, session policy, safe upload/processing, cache correctness, secrets, business logic, logging and recovery.
