Streaming Video With Cloudflare R2 - An Introduction

What R2 does, what Cloudflare Stream does, and why anyone would deliberately choose the do-it-yourself route

Cloudflare: The Foundation

Both Cloudflare R2 and Cloudflare Stream run on Cloudflare's global network. Before comparing them, it is important to understand what Cloudflare itself brings to the project.

Cloudflare provides the Internet-facing infrastructure that helps keep media fast, available, and protected. Its network automatically detects and mitigates DDoS attacks before they can overwhelm the application or media origin, while its global edge network places content close to viewers around the world. Cloudflare also provides security tools such as firewall rules, rate limiting, bot detection, and managed challenges when additional protection is needed.

This means we do not have to build our own global delivery network or DDoS defense system. Those capabilities are already part of the Cloudflare platform. The decision that follows is therefore not whether to use Cloudflare, but how to use it: Cloudflare Stream or our own R2-based media delivery system.

Cloudflare R2 vs Cloudflare Stream

Cloudflare R2 and Cloudflare Stream are two different Cloudflare products.

Cloudflare Stream is a managed video platform. Give it a video and Cloudflare can encode it, create multiple quality levels, package it for adaptive playback, store it, deliver it, provide playback URLs and a player, and report video analytics.

Cloudflare R2 is object storage. It stores files and serves files. It does not automatically turn a large video into a streaming-video system.

We can absolutely stream video from R2. That does not mean we are using the Cloudflare product named Stream.

The 30-second explanation

Cloudflare Stream

Upload the video. Cloudflare does most of the video work.

Stream automatically encodes and delivers adaptive-bitrate video, currently supporting H.264 renditions from 360p through 1080p.

Cloudflare R2 + Workers

We do the video work. Cloudflare stores and delivers the results.

We encode and package the video ourselves, upload the resulting files to R2, and use a Worker when we want authorization or custom delivery logic.

A bit more detailClick for a few basic definitions and the essential comparison.
What is a Cloudflare "Worker?"
A Worker is a small program that runs on Cloudflare's network and handles a request before the requested file reaches the viewer. In our media system, the Worker checks whether the viewer is allowed to watch, looks for a cached copy of the requested HLS segment, retrieves it from R2 when necessary, and sends the response back to the viewer.


What is a Cloudflare "Bucket?"
A bucket is just a flat container for files (called "objects"). Think of it as a top-level folder that can hold an unlimited number of files, but with no real subfolders - everything inside is addressed by a unique key (like photos/beach.jpg) in a single flat namespace.

What do we mean by "media workflow"?
It is the process that turns a finished master recording into something a customer can securely watch: prepare the video, encode the quality levels, package it for adaptive streaming, upload it to R2, authorize the viewer, deliver it through the player, and record useful viewer events.

What is HLS?

A browser can play one large MP4 file, but long-form video becomes much easier to deliver when it is packaged as HLS (HTTP Live Streaming).

Instead of asking for one enormous video file, an HLS-capable player reads a small playlist and fetches a sequence of small media segments as playback proceeds.

master playlist (.m3u8) | +--> 1080p playlist --> higher-quality option +--> 720p playlist --> baseline +--> 360p playlist --> slow-network fallback

If we create several quality levels, the player can switch between them as connection conditions change. That is adaptive-bitrate streaming.

For this introduction, our baseline is 720p with 10-second segments. 720p provides excellent viewing quality for ordinary web and mobile playback while keeping the payload smaller than 1080p. We can still offer 1080p when a larger screen or the content itself makes the extra detail worthwhile, and 360p remains available when network conditions require a lighter stream.

Why HLS fits R2 so well: the finished playlists and media segments are ordinary files. We create them ahead of time, store them in R2, and let Cloudflare deliver whichever pieces the player requests.

Our media is packaged as CMAF / fragmented MP4, which also leaves open the option to add MPEG-DASH later without re-encoding the underlying media segments.

R2 + Workers architecture is ideal for a media workflow

Using R2 means we are building the media workflow - but the heavy storage and delivery foundation still runs on Cloudflare's global network, the same network used by Cloudflare Stream.

We own and control that workflow, and Cloudflare provides the large-scale infrastructure underneath it: storage, edge execution, caching and global delivery.

The Cloudflare R2 foundation provides unlimited data storage per R2 bucket and unlimited objects per bucket. Workers run across Cloudflare's global network and scale automatically, with no general requests-per-second limit.

This means a major increase in viewers will not sidetrack us with infrastructure-related issues. Cloudflare absorbs that delivery growth within the same basic architecture.

Are they allowed to watch this content? | +--> NO --> deny access | +--> YES | +--> Cache HIT --> serve HLS segment <----------------------+ | ^ +--> Cache MISS --> fetch segment from R2 | | | +--> store clean copy in cache -------+ | v Viewer

The important architectural point: our application can stay focused on membership, authorization and the business rules that drive our business while Cloudflare carries the storage and request-delivery load.

What happens to costs when viewership grows 10X?

1,000 viewers | v 10,000 viewers Same R2 objects Same HLS playlists and segments Same Worker architecture Many more requests handled by Cloudflare

The infrastructure does not change just because the audience grows 10X or more - the usage does. More viewers mean more requests, more Worker activity, and potentially more R2 reads. But R2 does not charge bandwidth fees for Internet delivery. You only pay for storage and requests - not for the number of gigabytes sent to viewers.

Caching improves the picture even further. Popular HLS segments can be served directly from Cloudflare's edge cache instead of being read from R2 for every viewer. R2 is only asked for the segment again when Cloudflare does not already have a usable cached copy.

R2 storage is billed solely by the amount of data stored - gigabytes - there is no charge for "hours of video" in the library. Gigabytes. That's it.

So the practical growth question for an R2-based business model is unusually simple: "As viewing increases, how will storage and request charges increase?" More on this below.

Reasons to choose R2 + Workers over Stream

  • R2 is dramatically cheaper. Pennies per gigabyte-month, not dollars accumulating against every hour of video as it is stored and watched.
  • R2 does not charge an Internet egress fee. More video delivered does not create an R2 bandwidth bill.
  • R2 allows us to completely own authentication and authorization. Our application is the only authority deciding who may watch - there are no outside parties.
  • R2 eliminates video-platform lock-in. Our HLS assets are standard files that we control and can move wherever we choose, whenever we choose.
  • R2 allows us to completely control video quality for our audience. We choose the codecs, resolutions, bitrates, rendition ladder and encoding priorities.
  • R2 allows us to completely control video delivery for our audience. We have the freedom to shape our delivery system in ways that substantially reduce reads - and the monthly R2 bill.
  • R2 lets us favor quality without fearing a bandwidth penalty. For this project, 720p is our baseline viewing quality, with 1080p available as a higher-quality option when it is beneficial. On many video delivery systems, higher resolutions cost more because the larger files mean more data is being delivered, or because the provider charges more for the higher-resolution version. But with R2 + Workers, larger file sizes do not have the same effect on delivery cost. When HLS segment durations are equal, which is the norm in VOD delivery today, 720p and 1080p generate essentially the same number of reads, and since R2 bills reads - not bandwidth - the delivery request cost is essentially the same. We can therefore choose video quality for the right reason - the viewing experience - instead of deliberately lowering it just to control a bandwidth bill. And even better - since we control the delivery system - we can package higher-resolution video in longer HLS segments where appropriate, reducing the number of reads and potentially making the higher-quality version less expensive to deliver.

The trade: We willingly accept more technical responsibility in exchange for dramatically improved ownership and economics.

When Cloudflare Stream is the smarter answer

Stream is attractive when the business would rather pay for simplicity than operate a video pipeline. Cloudflare handles upload, encoding, adaptive delivery and video-specific infrastructure, and supports both on-demand and live video.

As of September 2026, Cloudflare's published Stream pricing is based on minutes stored and minutes delivered: storage capacity is sold at $5 per 1,000 stored minutes per month, and delivery is $1 per 1,000 minutes delivered. Encoding and ingress are included.

In plain English: If we do not want to become our own tiny video engineering department, Stream is the way forward.

When R2 + Workers is the smarter answer

R2 is attractive when the majority of your business workflow produces Video on Demand for your customers and providing it at the lowest practical cost is important. It becomes compelling when you also want to keep all of your media assets "in-house" and safely under your control.

For Standard R2 storage, Cloudflare currently lists $0.015 per GB-month, Class B reads at $0.36 per million operations, and imposes no bandwidth fees. HLS creates more read requests than one monolithic file, but the operation price is low enough that the meaningful cost comparison depends on the actual library size, viewing hours, encoding ladder and audience behavior. More on this below.

There is no universal winner. Stream provides convenience with confidence for those willing to pay for it. R2 provides total control on a shoestring budget for those with the confidence to leverage it. The right answer depends on the abilities and priorities of the customer.

Important distinction - Video on Demand (VOD) and Live Video are different processes Click to see why recorded and live video require different workflows.

Video on Demand is primarily a storage-and-delivery process. Live Video is a real-time processing-and-delivery process.

Video on Demand (VOD)

Create it | Process it | Store it | --- time can pass --- | Viewer requests it | Deliver it

Everything is known before anybody presses Play. We can transcode every rendition, build the playlists and segments, check the result, and only then publish it.

Live Video

Camera produces video NOW | Encoder pushes continuously | Process it NOW | Package it NOW | Deliver it NOW | Viewer watches

The system must ingest, process, package and distribute video while the source is still arriving. Playlists are changing and failure recovery matters in real time.

The initial version of this R2 Streaming Video application offers Video on Demand - available with adaptive playback quality comparable to major services such as YouTube, Vimeo and Cloudflare Stream - using a dramatically lower-cost storage-and-delivery model.

Live broadcasting may use a separate managed service - for example YouTube Live or Cloudflare Stream. When a live broadcast ends, the finished recording can be processed into HLS and moved into the R2 VOD library just like any other recorded video.

A later release will focus specifically on Live Video.

So what actually makes R2 cost money?

R2 separates two things that are often lumped together in a traditional video-delivery bill:

Requests are operations; bandwidth is payload.

With Standard R2, Cloudflare charges for the amount of data we store and for certain operations performed on that data. A read is a Class B operation. The first 10 million Class B operations each month are included, and additional reads currently cost $0.36 per million. But Cloudflare does not charge R2 bandwidth fees based on how many gigabytes those reads deliver to viewers.

Our baseline for the examples on this page: 720p Video on Demand with approximately 10-second HLS segments. One hour of video therefore contains about 360 media segments. The resolution determines how large those segments are; the segment duration determines how many segment requests the player makes.

This is where HLS becomes important to the cost model. HLS does not normally deliver one giant video file. It breaks the video into many small media segments that the player requests as the viewer watches.

1-hour newscast | v 3,600 seconds / 10-second segments | v about 360 segment requests per complete viewing | v 1,000,000 complete views | v about 360 MILLION segment requests

The ballpark number: suppose every one of those 360 million segment requests had to read the segment from R2 - a deliberately pessimistic scenario with no useful cache hits at all. After the monthly free allowance, the R2 Class B read charge would be only about $126 for one million complete views of a one-hour program.

That is the R2 read cost, not the entire delivery bill. In our design, each authorized media request also passes through a Cloudflare Worker. At current Workers Paid pricing, 360 million requests would add about $105 in request overage, plus the $5 monthly Workers plan, before CPU usage. In an intentionally brutal no-cache example, the combined R2-read and Worker-request portion therefore lands around $236, plus storage and any CPU overage.

Caching improves the R2 side considerably. When a popular HLS segment is already in Cloudflare's cache, the Worker can serve that cached copy without performing another R2 read. The Worker still handles the viewer's request and authorization, but R2 is not asked to retrieve the same segment again.

For scale: one million complete views of a one-hour video equals 60 million delivered viewing minutes. At Cloudflare Stream's published rate of $1 per 1,000 minutes delivered, that would be $60,000 in Stream delivery charges. This is not an apples-to-apples product comparison - Stream also supplies managed encoding, packaging, playback infrastructure and other conveniences - but it shows why the R2 cost model is so attractive for high-volume Video on Demand.

And now the obvious question: why does one one-hour viewing create roughly 360 requests instead of one? That is what HLS does.

What does caching actually save us?

A cache hit means Cloudflare already has the requested HLS segment close to the viewer, so the Worker can serve that cached copy without reading the same segment from R2 again.

Every cache hit avoids another R2 read.
Caching does not eliminate the Worker request in our design - the Worker still checks authorization - but it can dramatically reduce how often Cloudflare has to go back to R2 for the video itself.

Using our 720p / 10-second baseline, imagine one million people each watching a complete one-hour newscast. That produces about 360 million segment requests.

The number to remember: one million complete views of a one-hour program could generate about $126 in R2 read charges with no useful caching at all. At a 90% cache-hit rate, that same R2 read bill falls to about $9.36.

And scale that down to a more immediate business example: 10,000 people watching a complete one-hour newscast produces about 3.6 million segment requests. That is still below R2's current monthly allowance of 10 million free Class B reads - even before caching helps.

Cloudflare's edge network makes this especially attractive for Video on Demand. Popular segments can be served repeatedly from locations close to viewers instead of being fetched from R2 again and again. The more popular a piece of content becomes, the more valuable that cache can become.

The practical point: R2 is already inexpensive without caching. Edge caching makes an already inexpensive delivery model even more efficient as audience size grows.

What actually happens with our R2 approach?

Source/master video | v FFmpeg (a free utility, universally used to prepare videos for streaming) | +--> 360p HLS playlist + segments (fallback) +--> 720p HLS playlist + segments (baseline) +--> 1080p HLS playlist + segments (higher-quality option) | v Cloudflare R2 bucket | v Cloudflare Worker / access check | v HLS-capable web player (for example Video.js)

The player reads the master playlist for the selected video, chooses an appropriate quality level, downloads a few small segments, and then, while the viewer watches, keeps requesting more segments. If bandwidth changes, the adaptive player dynamically switches renditions, usually with no noticeable interruption.

This is real streaming video - we simply built the packaging pipeline ourselves instead of buying Cloudflare Stream's managed pipeline.

A useful mental model

FFmpeg = the video factory

It creates the quality levels we want and packages them into HLS playlists and small media segments.

R2 = the warehouse

It holds the master video, playlists, segments, thumbnails, audio, or any other objects we decide to store.

Workers = the gatekeeper

A Worker can enforce access, map friendly URLs to R2 objects, handle headers, and return the files an authorized viewer is allowed to request.

Cloudflare = the delivery network

Cloudflare carries the requests across its distributed network and caches popular HLS assets close to viewers so repeated viewing can avoid unnecessary trips back to R2.

HLS = the adaptive streaming protocol

Its playlists tell the player which quality levels and small media segments are available and where to request them.

Web player = the audience view

An HLS-capable player on our site - for example Video.js - reads the playlists, requests segments, displays controls, and plays the video for the viewer.

Why R2 works so well for audioClick to see the simpler audio precedent.

R2's Workers API supports ranged reads (specific segments, "substrings") of stored objects (our audio and video files). When a player needs only part of a file, the Worker can request and serve that portion rather than reading the entire object.

That already works very well for audio:

One complete audio file stored in R2: [========================================================] Player seeks to a new position: [=====] ^ | only this byte range is requested R2 does not need to read and return the entire file.

Video can use the same underlying capability, and properly packaged HLS goes further: instead of treating a long recording as one enormous object and relying heavily on byte-range requests, HLS divides it into small media segments that the player requests as needed.

Why one giant MP4 becomes less attractive

A browser can play an MP4 from R2 and can use HTTP range requests to seek within it. For short videos, that may be perfectly adequate.

Long video changes the economics and behavior. Cloudflare currently documents a 512 MB maximum cacheable file size for Free, Pro and Business plans. A large MP4 above that limit cannot receive the same single-object edge-cache benefit.

HLS avoids that problem naturally: the video is divided into many small segment files, each comfortably below the cache-size limit. Seeking also becomes a matter of requesting different segments rather than repeatedly addressing byte ranges inside one enormous object.

Important: The 512 MB number is a CDN cacheable-file limit, not an R2 object-size limit and not a statement that R2 cannot store large video files.

What R2 + Workers does NOT magically solve

  • It does not decide which video resolutions we should produce.
  • It does not transcode the master video for us.
  • It does not create an adaptive-bitrate ladder for us.
  • It does not create HLS playlists and segments unless our pipeline does that work.
  • It does not supply a complete video analytics product.
  • It does not turn object storage into a turnkey live-streaming service.
  • It does not design our authentication, entitlement or membership rules.

That is the recurring theme of this series: R2 gives us excellent building blocks. We are choosing to assemble them.

Analytics are designed in from Version 1Click to see how viewer behavior is preserved from day one.

Version 1 begins recording important viewer events from the start - plays, pauses, viewing progress, completion, seeking, playback errors and other useful actions.

The first release does not need a full analytics dashboard. What matters is that the underlying event history is already being preserved, so valuable early behavior is not lost while the platform is young.

Those events can later support reports such as watch time, completion rates, popular content, viewing trends, playback quality, individual viewing history and member engagement.

User behavior analytics are important to us and they deserve their own release - we are targeting Q4 2026.
