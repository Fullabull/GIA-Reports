Why Cloudflare?

BeyondTheMatrix.video infrastructure notes - why we are comfortable putting Cloudflare at the edge, what it does for us, and what remains our responsibility.
The short version: We are not choosing Cloudflare merely because it has a very large network. We are choosing it because the company has repeatedly demonstrated automatic mitigation of enormous real-world attacks, its protection is distributed throughout the edge rather than dependent on one central scrubbing point, it gives us a programmable security layer in Workers, and R2 lets us eliminate a conventional public media origin altogether.

1. Why Cloudflare earns a place near the top of the list

Battle tested

Real attacks, not just capacity claims

Cloudflare reported automatically mitigating 47.1 million DDoS attacks during 2025. Its 2025 Q4 report describes attacks exceeding 200 million HTTP requests per second and a 31.4 Tbps network-layer attack, which Cloudflare says was detected and mitigated automatically.

Distributed defense

Autonomous protection at the edge

Cloudflare's home-grown dosd system runs on every server throughout its global network and can detect and mitigate attacks without waiting for centralized consensus. A global system watches across the whole network for widely distributed attacks.

State awareness

flowtrackd

flowtrackd adds stateful traffic analysis alongside dosd. Cloudflare uses it in advanced systems that learn normal traffic patterns and identify sophisticated TCP and DNS attacks.

Transparency

They publish the ugly stuff too

Cloudflare publishes detailed incident reports when its own systems fail. After major 2025 outages it launched its "Fail Small" engineering program and reported completing the program in May 2026. Trust is helped by knowing how a vendor fails, not by pretending it never does.

4. UDP: good technology, but intentional architecture

Cloudflare does not treat UDP as inherently malicious. It protects large amounts of legitimate UDP traffic and explicitly mitigates UDP reflection and flood attacks. The important design issue is that UDP has no TCP-style handshake, so legitimate high-volume UDP can look much more like an attack if its application behavior is not known.

For a future custom UDP ingest service, Cloudflare Spectrum can proxy arbitrary TCP and UDP applications through Cloudflare's edge, but custom protocol use is an Enterprise-level product. That is something to evaluate when BeyondTheMatrix.video reaches the point where a purpose-built UDP ingest path is economically justified.

For the first large archive migration, the simpler strategy is parallel R2 multipart upload over HTTPS: multiple parts in flight at once, automatic retries of failed parts, resumability, and support for objects up to 5 TiB.

A very timely R2 feature: Local Uploads

Beta as of September 18, 2026. R2 Local Uploads can write object data to storage near the uploader and asynchronously copy it to the bucket's primary location. Cloudflare specifically describes it as a way to improve upload performance and reliability when clients are far from the bucket. It works with PutObject and multipart UploadPart, and Cloudflare currently charges no additional fee for enabling it beyond ordinary R2 operation costs.

5. Why we still want Adaptive Traffic Monitoring

Cloudflare and Render should absorb the brute-force network attack. Adaptive Traffic Monitoring watches for the attack that looks enough like a real user to get through.

Our monitor should therefore be considered an application-awareness layer, not our primary DDoS shield. It can watch normal traffic velocity and detect deviations such as sudden endpoint-specific spikes, unusually expensive request patterns, authentication abuse, repeated errors, suspicious user-agent/IP behavior, or a rapidly changing request distribution.

A useful response ladder is:

The monitor should log the real client identity available through trusted proxy headers, request endpoint, response status, response time, resource cost where practical, and Cloudflare request identifiers. Its purpose is not simply "requests per minute"; it is to recognize when the shape of legitimate-looking traffic changes.

6. What if somebody discovers our server IP?

For an ordinary Render web service, this concern is smaller than it would be on a conventional VPS. Render documents that the application's HTTP port is not directly reachable from the public internet. Public traffic reaches the Render load balancer first, and all inbound Render web-service traffic passes through Cloudflare for DDoS protection.

So discovering an underlying instance address is not equivalent to discovering a routable Apache/nginx origin that can simply be attacked directly.

There is, however, another bypass worth remembering: a Render service has its own onrender.com hostname. If the BeyondTheMatrix.video hostname is protected by rules in our Cloudflare account, somebody who knows the Render hostname may bypass those particular account-level rules and go directly to Render's edge. They still encounter Render's Cloudflare-backed DDoS protection, but our application should not assume every incoming request passed through our own Cloudflare policy layer.

That is another reason Adaptive Traffic Monitoring and application-level rate controls remain valuable.

7. Why Render?

Render does not replace Cloudflare in our design. It gives our application server a second protected hosting layer, while removing much of the traditional server-management burden.
  • Every public Render web service already receives built-in DDoS protection. Render says it uses Cloudflare behind the scenes and includes this protection automatically on all plans.
  • Layer 3/4 floods are handled before the app. Render specifically lists SYN floods and UDP reflection as traffic that Cloudflare drops before it reaches application compute.
  • Large obvious Layer 7 floods also receive edge filtering.
  • Targeted application-layer abuse remains ours. Render explicitly calls out credential stuffing, abusive API requests, expensive queries and slow requests as application responsibilities.
  • The actual service port is not directly public. Render's load balancer forwards inbound requests to it.
  • Render forwards useful tracing information. It recommends logging the CF-Ray identifier and using x-forwarded-for for the real client IP.
  • Higher-tier Render plans can add inbound IP rules for web services if we later need tighter network allowlisting.

Therefore: we should keep Adaptive Traffic Monitoring, but we do not need to pretend our Python application is a miniature Cloudflare. Let Cloudflare and Render stop the packet floods. Our code concentrates on the attacks only the application can truly understand.
