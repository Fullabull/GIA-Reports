Search and Security

How the GIA Search system is built, monitored, and protected. This page describes the controls currently in place and the work continuing behind them.

Summary

GIA Search is not just a search box placed on top of a collection of reports. It is a monitored application with client-side caching, server-side search, performance telemetry, administrative diagnostics, request filtering, attack-signature detection, persistent security logging, and Cloudflare-backed client identification.

The goal is straightforward: make hundreds of reports fast and useful to search, while keeping obvious hostile traffic away from the application and leaving enough evidence behind to understand failures, attacks, and performance problems when they occur.

1) Search architecture

The search corpus is divided into multiple compressed archive segments instead of loading one giant historical file every time Search opens.

Historical archives

Older report archives are allowed to remain in the browser cache and can be reused locally on later visits instead of being downloaded again.

Newest archive

The newest archive can be reused from cache, but the browser revalidates it so newly published material is not silently missed.

Client-side search

Normal searches operate against the loaded corpus in the browser for fast interaction.

Server-side search

More complex searches can use the Render application, allowing Search to handle work that would be awkward or expensive to perform entirely in the browser.

This design keeps ordinary Search responsive while still allowing the system to scale into more complex search and diagnostic work.

2) Performance and failure monitoring

Search records structured performance information so slowdowns can be diagnosed instead of guessed at. Measurements include load timing, archive cache behavior, search timing, server processing time, failures, browser family, and anonymous browser-profile identifiers.

Administrative statistics summarize the data with averages, medians, 90th-percentile measurements, maximums, cache behavior, browser counts, and failure rates. Date-range exports allow performance history to be retained for comparison over time.

Why this matters: when Search feels slow, the system can distinguish browser/cache behavior, network delivery, and server processing instead of treating "slow" as one mystery.

External JavaScript and CSS resources used by Search are pinned and protected with Subresource Integrity where appropriate. Search also installs an early resource-failure guard so a blocked, missing, or corrupted external resource can be recorded in client-errors.log.

3) Request security layer

Public requests pass through a server-side security layer before normal application processing. Requests matching blocked rules are rejected with HTTP 410.

Client identity is based on Cloudflare's CF-Connecting-IP value rather than trusting the first value supplied in X-Forwarded-For. This was tested directly: a forged X-Forwarded-For address was ignored, while the server continued to record the actual connecting address.

General request controls

  • Persistent IP blocklist enforcement.
  • Requests with no User-Agent are rejected.
  • Disabled crawler categories are rejected.
  • Known offensive scanner User-Agents are rejected.
  • Directory-traversal markers are rejected.
  • Known attack paths and query signatures are rejected.

5) Administrative security

  • The /admin area is session protected.
  • Admin passwords are checked using a password hash rather than plaintext comparison.
  • Five failed login attempts from the same client IP trigger a 15-minute lockout.
  • Admin sessions use a 20-minute lifetime.
  • The administrative block-IP POST path requires a CSRF token.
  • Admin file browsing is limited to explicitly allowed logs and admin directories.
  • Resolved-path checks prevent administrative file browsing from escaping those approved locations.

The persistent IP blocklist is already enforced. Administrative tooling for adding addresses to that blocklist is still being expanded.

6) Security and audit logs

Security decisions are not limited to console output. Blocked requests and administrative security events are written to persistent security.log, while administrative activity is written to audit.log.

Security records include:

  • UTC timestamp
  • event type
  • trusted client IP
  • HTTP method
  • request path
  • matched rule or event detail
  • User-Agent where applicable

Log fields are sanitized before being written so tabs, carriage returns, and newlines cannot be used to manufacture extra columns or fake log records.

A simple test request for /wp-login.php was rejected with HTTP 410 and produced a persistent BLOCK_SIGNATURE record containing the timestamp, actual client address, requested path, matched WordPress rule, and curl User-Agent.

7) Continuing expansion

The current rule set is a starting layer, not the finish line. The system has accumulated a very large body of hostile and automated request traffic over time, and that history provides a much larger pool of real-world behavior to analyze.

Future work will continue turning observed attack traffic into better classification, logging, diagnostics, and defensive rules. In other words: what is shown on this page is the visible tip of a much larger iceberg.
