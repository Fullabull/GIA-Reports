UNN Streaming Base Platform: Build vs Buy

Focused architecture and cost flyover - September 8, 2026

The requirement changed - and that is useful

UNN is not primarily looking for a replacement website/community product. The technical requirement is closer to:

"A streaming base platform to build our own back and front end on it."

That moves the discussion away from Kajabi, GoHighLevel and other finished creator platforms and toward video infrastructure, APIs, storage, authentication and application architecture.

The question is now: which pieces should UNN buy as managed services, and which pieces should UNN build and control itself?

The actual UNN usage pattern matters

  • Live: an occasional Q&A, perhaps a few hundred viewers, once every few months.
  • Regular programming: prerecorded news and supported-topic videos/"podcasts" that viewers choose individually.
  • Future scale: important, but potentially much larger live audiences are still a future problem rather than today's operating load.

VOD economics may matter more than live-event economics right now. UNN should be careful not to buy a television-network-sized solution merely because it might someday need one.

Part One - Cloudflare as the base platform

Cloudflare Stream is specifically designed so developers can build their own video experience. It handles upload, live ingest, encoding, adaptive-bitrate delivery, storage and playback through APIs.

Why this architecture is attractive for change

Cloudflare does not need to know what a "Premium UNN Member" means.

UNN backend asks: "Is this member entitled to this video?" YES -> issue a signed Stream token -> play video NO -> no token -> show upgrade / wait / access message

Kim can change access policy without changing the streaming platform:

paid users immediatelyfree users after 7 days30-day full trialtemporary event accesssupporter tiergrace period

The entitlement rule belongs to UNN. Stream simply obeys a valid signed token.

Cloudflare pricing model

  • Storage: $5 per 1,000 stored video minutes.
  • Delivery: $1 per 1,000 delivered viewing minutes.

Ingress and encoding are included, and Cloudflare says there are no additional video-egress/bandwidth fees on top of delivered minutes.

One hour watched by one person is 60 delivered minutes, or about $0.06 at current retail pricing.

Live Q&A: Cloudflare is already more than large enough

For genuinely interactive Q&A latency, Cloudflare's newer Stream Live WebRTC path is designed for sub-second playback to thousands of concurrent viewers.

UNN's current "few hundred people every few months" requirement is therefore not a scale problem. It is primarily a cost, workflow and integration choice.

The amusing part

There is already a tiny proof-of-concept of the general philosophy inside the GIA archive work:

private Cloudflare storage | Worker gateway | custom application decides what the user can reach

That little audio gateway is obviously not a production UNN video platform. But the architectural instinct is the same: UNN owns the application behavior; Cloudflare provides infrastructure underneath it.

Part Two - Serious API-first alternatives

Cloudflare Stream

Strength: unusually cohesive whole-stack option.

Video plus Workers, R2, D1, Durable Objects, CDN and security under one infrastructure umbrella.

Mux Video

Strength: video specialists.

Very clean API-first live/VOD product with signed playback, webhooks, analytics and a strong developer model.

Amazon IVS

Strength: live/interactive infrastructure.

Managed low-latency video, realtime stages, optional managed chat and recording into S3.

Cost surprise: Mux deserves a very serious look at today's scale

Mux currently includes the first 100,000 delivered minutes each month free. After that, base 720p delivery begins at $0.0008/minute and 1080p at $0.001/minute. Live input has a separate charge; 720p Plus live currently starts at $0.025/minute.

That means a small occasional live event may cost very little on Mux even though Mux is a premium developer-video platform.

For prerecorded programming, the economics may point somewhere else

Most UNN consumption today is prerecorded. That changes the comparison because video delivery repeats every day while live transcoding happens only occasionally.

The build-yourself / cost-optimized alternative

OBS / studio feed | v Nimble Streamer + Live Transcoder (on a UNN-controlled server) | creates adaptive HLS | v Bunny CDN | v UNN viewers

Bunny is not operating the live event. Nimble is the live media server/origin. It receives the live feed, optionally creates multiple resolutions, packages HLS and exposes the changing playlist/segments. Bunny performs the inexpensive global distribution.

Why this is financially interesting

  • Nimble Streamer: about $50/month per server; Softvelum examples put one instance plus basic WMSPanel around $70/month.
  • Live Transcoder: $50/month per transcoder license when adaptive transcoding is required.
  • Server/VM: additional - depends heavily on CPU/GPU and redundancy.
  • Bunny Volume CDN: $0.005/GB for the first 500 TB.
  • Bunny Standard: $0.01/GB in Europe/North America, with higher regional rates elsewhere.

Using the same illustrative Q&A and assuming an average delivered bitrate of 3 Mbps, the event would move roughly 405 GB of viewer traffic.

That is about $2.03 on Bunny Volume or about $4.05 on Bunny Standard in Europe/North America for CDN delivery - but software, server capacity, engineering and reliability still have to be paid for.

The price of cheap bandwidth is operational responsibility

  • origin-server availability and failover
  • transcoding CPU/GPU capacity
  • adaptive-bitrate ladder design
  • monitoring and stream health
  • encoder reconnect behavior
  • recording/archive workflow
  • origin security
  • software patching and upgrades
  • load testing before an event

This is not a hack. Nimble explicitly positions itself for self-managed streaming infrastructure, CDN-origin and multi-CDN architectures. But somebody on the UNN technical team becomes responsible for making it boring and reliable.

Bunny has one contractual issue to clear first

Bunny's current Acceptable Use Policy says that using Bunny for live video streaming of short events is not allowed without prior written consent.

"We intend to distribute live HLS generated by our own Nimble/Wowza origin through Bunny CDN for occasional member events. Is this approved for our account, and under what terms?"

If Bunny says yes, this option becomes much more interesting. If Bunny says no, it leaves the board.

A potentially sensible hybrid

PRERECORDED UNN master archive | v Bunny Stream / Bunny CDN | v very inexpensive VOD delivery OCCASIONAL LIVE OBS / studio | v Managed live (Cloudflare / Mux / IVS) OR Nimble origin + approved CDN path | v UNN viewers

Because UNN is VOD-heavy and live-light, there is no law saying one vendor must do everything. This lets UNN optimize the everyday prerecorded workload without forcing today's small Q&A requirement to dictate the whole architecture.

What I would test next - before anybody chooses

  1. Upload one prerecorded UNN-style video.
  2. Protect it behind UNN's own entitlement decision.
  3. Play it on desktop and mobile through UNN's own page.
  4. Run one private live test with 25-50 invited viewers.
  5. Automatically retain the live recording.
  6. Measure actual bitrate, viewer-minutes, CDN bytes and resulting cost.
  7. Export or copy every master asset and metadata record.
  8. Then model cost using real UNN monthly VOD viewing, not guesses.

The likely winner may not be one provider. At UNN's current usage pattern, a consciously designed hybrid could be cheaper, more portable and better aligned with the "build our own front and back end" requirement.
